## Answer

**Python 3.13, and nothing else. There is no install step at all.**

### The runtime

`docs/decisions/0001-runtime-and-packaging.md` (DR-0001) settles it: **"Python 3.13, at every
level."** The record is explicit that this is *not* a floor that higher levels may raise —
it is "the same version throughout," on the reasoning that "a project that runs on 3.13 at one
level and 3.11 at another has two runtimes to explain and two sets of instructions to keep
true." The record closes that section with "CI runs 3.13, so the supported version is the
tested one."

The same number is repeated everywhere the level 2 build is described:
`README.md` ("**2 — build** … Python 3.13" in the levels table, and "Python 3.13, standard
library only. No install step."), `dropin/README.md`, `.okfm/level-2-build/index.md`,
`docs/okfm-guide/README.md`, `spec/okfm-v0.2.1.md` (the repository map comment: "Python 3.13,
standard library only. No requirements file, by design."), and module docstrings in
`dropin/build.py` and `dropin/okfm_core.py`.

An important nuance DR-0001 states about itself: **the 3.13 pin is a policy choice, not a
technical requirement.** Under "## On 3.13" — "Nothing in `dropin/` currently uses anything
newer than Python 3.9, so the pin is not technical — it is a decision to have **one**
supported version rather than a floor per level." The rejected alternative was a low floor at
level 2 and a higher one above; it was rejected as costing "two runtimes to document, two CI
matrices, and a class of bug that only appears on the version nobody tests."

### What has to be installed: nothing

DR-0001's decision section: "**`dropin/` (Level 2) is standard library only.** No
`requirements.txt`, no install step beyond having Python." `docs/decisions/0009-adoption-levels.md`
states the level-2 contract as line items — "**Adopter supplies:** Python 3.13, and their own
credentials if they resolve live pointers. **Installs:** nothing. Standard library only."

Two constraints in DR-0009 explain why this is load-bearing rather than incidental:
**liftable** (the folder is pasted into a stranger's repository, so it may not reach outside
itself) and **no install step** (a dependency means that stranger resolves a package tree
before anything happens, "which is the friction this level exists to remove"). DR-0001 makes
the same point and adds the escape hatch: if frontmatter writing ever needs more, "the answer
would be a vendored parser, not a dependency."

This is demonstrated, not just asserted. DR-0001 cites that `dropin/` "parse[s] frontmatter
for 26 concepts across 3 bundles using about 40 lines of regex and no PyYAML," because the
YAML subset OKF frontmatter uses is small — "scalars, lists, one level of nesting, and flow
mappings." `dropin/check_bundles.py` says the same in its docstring: "Deliberately stdlib-only
and regex-based -- no PyYAML." Confirmed by reading the imports across every file in `dropin/`:
only `json`, `re`, `sys`, `os`, `time`, `uuid`, `argparse`, `difflib`, `hashlib`, `subprocess`,
`pathlib`, `datetime`, `urllib.*` — plus intra-folder imports (`okfm_core`, `config_schema`,
`build`, `bootstrap`, `enrich`, `refresh`, `telemetry`). No third-party import anywhere.

### Consequently, the whole procedure is copy and run

```bash
cp -r dropin my-project/.okfm && cd my-project
python .okfm/okfm.py             # build → refresh → view → check
python .okfm/okfm.py --check     # same, writes nothing, fails on mismatch (CI)
```

There is no packaging step being skipped here: `dropin/okfm.py` dispatches each step by
shelling out with `subprocess.run([sys.executable, str(HERE / script), *args])`, so it works
as a plain folder of scripts with "no assumption that it was installed as a package"
(DR-0009). The pipeline steps are listed in `STEPS` in `dropin/okfm.py`: `check_config.py`,
`build.py`, `refresh.py`, `bake_web_ui.py`, `check_bundles.py`.

### Why nothing else appears — the `needs` rule

Every component the deterministic pipeline runs is `needs: []` under
`docs/decisions/0008-build-pipeline.md`: no network, no secrets, no model. That is why Python
is the entire prerequisite list. Enrichment is deliberately excluded, because "a composite's
`needs` is the **union** of everything it invokes" — adding a model step would make the whole
pipeline `needs: [model]` and take it out of CI on a fork's pull request
(`docs/okfm-guide/level-2-build/the-pipeline.md`, `dropin/okfm.py` docstring). This boundary is
enforced in CI by `dev/check_levels.py`, which reads the `needs-*` tag on every component and
fails when one exceeds its level.

### The three things that are *not* required by the deterministic build

- **A model / Ollama.** `dropin/enrich_local.py` is "the one component in `dropin/` that
  declares `needs: [model]`" and is kept out of `STEPS` on purpose. That path (level 2+) needs
  a running Ollama at `enrich.base_url` with the model **already pulled** — "nothing here
  downloads one" — plus `OLLAMA_HOST=0.0.0.0` if it is on another box. Not part of the
  deterministic build.
- **`git`.** `dropin/guard.py` shells out to `git diff --unified=0`, but `guard` is a level 3
  command in `EXTRA`, outside the pipeline.
- **A browser/toolchain for the web UI.** Level 1 needs only a browser; `okfm-web-ui.html`
  opens from disk with "no server, no build, no dependencies," and DR-0001 notes the web UI
  "is already dependency-free HTML and needs no toolchain of its own."

### Two caveats stated in the sources

1. **The rule is scoped to levels 1–2.** DR-0001: "Levels 3–4 may take dependencies freely …
   The line worth holding is not 'OKFM installs nothing' but 'the level you start at installs
   nothing.'"
2. **Packaging above level 2 is unsettled.** DR-0001's status is "partially settled" and its
   "Still open" section names Level 4 packaging — `uvx okfm` and `pipx install okfm` are the
   candidates and "the name's availability on PyPI is unchecked."

Why Python at all (DR-0001, "Why Python"): attesters are Python by specification (§6.6, §9), so
a Python implementation runs them without a bridge. Node/TypeScript was rejected because
attesters would need a second runtime; Go and Rust were rejected for the "worst attester story"
and a compile step between an adopter and a fix.
