## Answer

"Publishing" a bundle is two independent facts in `okfm.json`, and un-publishing means changing both. Neither one deletes anything on disk except one narrow case.

### The two keys, and why they are not the same key

- **`bundles.<id>`** is what the mesh *is*. `okfm_core.configured_bundles()` returns `cfg["bundles"]` verbatim whenever that key is present, and that map is the input to every reader: `check_bundles.py` (validation), `bake_web_ui.py:collect()` (the `BOOTSTRAP` index baked into `okfm-web-ui.html`), `refresh.py` (drift observation), and `enrich.py` (the level-3 work list). Delete the line and the bundle disappears from all four.
- **`build.exclude`** (or `build.root_files: false` for the loose-files bundle at the top of `build.root`) is what gets *read*. `okfm_core.discover_sources()` runs live on every build — it is not frozen into the config — so dropping the source folder from the scan is what stops `build.py:mirror()` / `write_index()` regenerating the concepts. Entries are matched both root-relative and project-relative (`skipped()` inside `discover_sources`), and `config_schema._check_shape` rejects absolute paths and `..`.

This seam is documented deliberately, not accidental: `config_schema._cross_checks` emits `build.exclude[i]` → *"excluded from the build, but `bundles.<bid>` still names it — every reader still shows it"*, with the hint *"`exclude` controls what is READ; `bundles` is what the mesh IS."*

Doing only one of the two is worse than doing neither:

- **Only `exclude`:** the build stops writing it, but the folder stays on disk and stays listed, so every reader still shows it. You get the cross-check warning above plus `check_config.orphaned_bundles`: *"this build no longer writes it, but it is still listed and still on disk"*, hinting `Remove the bundles.<bid> line and delete <path>`.
- **Only remove the `bundles` line:** the build still discovers and rewrites `.okfm/<id>/` on the next run, and `build.py:write_mesh` re-creates `mesh/members/<id>.md` carrying `registers -> /<id>/index.md`. Because `check_bundles.py` builds `mesh_paths` from `configured_bundles`, that target now resolves to nothing and validation **fails** — reported against the mesh bundle, two steps from the config line you actually changed.

### Order that leaves the least mess

1. Add the folder to `build.exclude` (relative to `build.root`), or set `build.root_files: false` for the root-files bundle.
2. Run `python dropin/okfm.py build --apply`. Nothing is pruned yet — `prune_members` computes `known = set(configured_bundles(cfg)) | {built names} | {mesh_dir.name}`, and the id is still in `bundles`.
3. Delete the `bundles.<id>` line.
4. Rebuild. Now the id is in neither set, so `prune_members` removes `.okfm/mesh/members/<id>.md`, and the regenerated `mesh/index.md` no longer lists it.
5. `rm -rf .okfm/<id>/` yourself, and re-run the pipeline (`view` re-bakes the viewer, `check` confirms nothing dangles).

### What the tooling cleans up for you

Exactly one thing: the mesh member concept. `build.py:prune_members` deletes `.okfm/mesh/members/<id>.md` on an `--apply` build, and its docstring is explicit that this is the *only* place the build deletes anything — `.md` files, in the mesh's own `members/` folder, that this process wrote. `mesh/index.md` is rewritten each build from `built`, so the member list follows automatically (it is `_owned`).

### What is left behind for you

1. **`.okfm/<id>/` — the concept folder itself.** The build never deletes bundle directories. Worse, the only thing that would have told you it is there — `check_config.orphaned_bundles` — returns `[]` when `"bundles" not in cfg` and only reports ids that are still *in* the `bundles` map. So the moment you delete the `bundles.<id>` line, the leftover directory becomes invisible to the validator. Delete it by hand.
2. **A member concept somebody touched.** `prune_members` only removes files where `build._owned()` is true: no `verified:` key, and `generated:` containing `process:okfm-build`. A member edited by a person, or stamped by a level-3 enrichment pass, or hand-written for a hand-authored bundle, is printed to stderr as `stale <path> — registers '<id>', which is not a bundle any more. Not mine to delete; remove it yourself.` Leaving it is not cosmetic — that stale `registers` edge is the dangling-relation failure `check_bundles.py` errors on.
3. **Incoming edges from other bundles.** Any concept elsewhere with `okfm_relations: - { predicate: ..., target: /<id>/... }` becomes a hard error, `relation target ... resolves to nothing`. The reason is subtle: `check_bundles.py` resolves an absolute target as mesh-absolute only when its first segment names a configured bundle (`mesh_tgt = tgt if head in bundles else f"{root}{tgt}"`), so once `<id>` is no longer an id, `/<id>/x.md` is re-read as relative to the *referring* bundle's root and then fails. Cross-bundle body links fail the same way (`broken link [...](...)`, checked with `(f.parent / tgt).resolve().exists()`). Fixing or removing those concepts is manual.
4. **The committed viewer.** `okfm-web-ui.html` carries the mesh in its baked `BOOTSTRAP` block (and your raw config in `CONFIG`). It is stale until you re-run `okfm.py view`; `bake_web_ui.py --check` fails CI with `STALE: committed viewer does not match the project`. If you delete the directory but leave the `bundles` line, `collect()` prints `warn: bundle '<id>' -> <path> does not exist` and `check_bundles.py` errors with `<id>: configured path does not exist`.
5. **The observation cache.** `refresh.py` loads `dropin/.okfm-cache/observations.json`, adds entries keyed `"<uri>@<id>/<file>.md"`, and saves — it never removes anything. Entries for the retired bundle persist indefinitely. They are inert (lookups in `bake_web_ui.drift_of` and `enrich.work_list` are driven by concepts that still exist), and `load_cache` treats a corrupt or missing cache as rebuildable, so deleting the file is safe if you want it clean.
6. **Prose that names the bundle.** `README.md`'s repository map and `docs/okfm-guide/level-1-view/the-shipped-mesh.md` ("Seven bundles registered in `okfm-mesh/`") list bundles by hand. `dev/check_docs.py` only lints the four spec-corpus documents, so nothing checks these.

### Three special cases

- **If the bundle you are dropping is the registry.** `okfm.json` sets `federation.registry: "./.okfm/mesh"`. `check_bundles.py` resolves that to a bundle id and, finding none, sets `registry = None` — which silently skips the entire "the mesh must name every bundle" check (spec §12.2). Update `federation.registry` at the same time, or you lose a check without being told.
- **In-place bundles.** For a bundle whose files *are* the concepts (`docs/decisions` here, already in `build.exclude`), there is nothing for the build to stop writing — publishing is purely the `bundles` entry, and the sources are your own documents, which the build never owns and never deletes.
- **If you only want it out of statistics and agent context, do not un-publish it.** The intended mechanism is scope: concepts carry `okfm_scope`, and `read.exclude_scopes` (currently `["guide"]`) keeps them out of health statistics, the index budget, benchmark corpora, and any context assembled for an agent, while still rendering. Spec §14.5 and `the-shipped-mesh.md` describe exactly this for the bundled guide.

### One caveat if you reach for `build.sources` instead

Writing an explicit `build.sources` list turns discovery off entirely, which is another way to stop a bundle being built — but `check_config.orphaned_bundles` does `{s["bundle"] for s in resolve_sources(cfg)}`, while `okfm_core.resolve_sources` returns `{"path": ..., "type": ...}` (no `bundle` key) for entries given as plain strings or as dicts that omit it. `build.py` guards this with `entry.get("bundle")`; `check_config.py` does not, so `okfm.py config` would raise `KeyError` — and it is the first step in the pipeline. `build.exclude` is the safer route.
