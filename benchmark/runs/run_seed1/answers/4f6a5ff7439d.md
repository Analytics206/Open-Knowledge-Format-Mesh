## Answer

The component is `dropin/enrich_local.py` (reachable as `okfm.py enrich-local`), which drafts
`description` and `tags` by calling an Ollama endpoint on your own machine. You are right that it
costs nothing and holds no key — the project agrees, and gave it the name **Level 2+**. What it
did not give it is the *location* level 2, and the reason is that the ladder and the price tag
measure two different things.

### 1. The 2/3 boundary is a mechanical check on the `model` tag, not a judgement about cost

`dev/check_levels.py` is the enforcement. It hardcodes

```python
LEVELS  = {"level-1-view": 1, "level-2-build": 2, "level-3-enrich": 3}
LADDER  = ["nothing", "human", "model", "secrets"]
ALLOWED = {1: set(), 2: {"human"}, 3: {"human", "model", "secrets"}}
```

and for every `.md` in a level bundle it reads the exposure out of the ordinary `tags:` list via
`needs_of()` (any tag beginning `needs-`), then applies `real - ALLOWED[level]` and fails on a
non-empty remainder with `"needs [...], which level N does not allow"`. The concept
`.okfm/level-3-enrich/a-local-model.md` carries `tags: [needs-model]`. Move that concept into the
`level-2-build` bundle and `ALLOWED[2] == {"human"}` makes `over == {"model"}`, so the script
appends an error and `main()` returns 1. The rule is `needs ⊆ allowed(level)` — a *floor*, not an
equality, which is why deterministic tools like `guard.py` may sit at level 3, but never why a
`model` component may sit at level 2.

Note the check reads no notion of money at all. There is no `okfm_level`, no `okfm_needs`, no cost
field — only the four-value exposure vocabulary from DR-0008 (`nothing < human < model < secrets`),
ordered by how far a component reaches past pure local computation.

### 2. Rewriting the rule around "key / no key" was considered and refused

DR-0013 ("The question": *"Ollama removes the key without removing the model"*) states the two
options plainly: putting a model-calling component at level 2 either **breaks the check, or forces
it to be rewritten around "key / no key" instead** — and calls the second worse, because *"a rule
loosened to admit the first thing that did not fit is no longer a rule."* DR-0009's "Where this
meets DR-0008" section is what the check implements: *"The Level 2 / Level 3 line is the `model`
line, exactly"*, and its whole stated purpose is to keep "never needs an API key" mechanically true
"as the implementation grows, rather than a promise that quietly rots."

### 3. The distinction you are pointing at already exists — one rung up, not one rung down

The thing that makes local drafting feel cheap is the *absence of* `secrets`, not the presence of
`model`. `needs: [model]` **without** `needs-secrets` has been a legal set since DR-0008 was
written; DR-0013 observes that local Ollama "does not need a new position on the ladder; it is the
first component OKFM ships that actually occupies that one. What changed is that the rung stopped
being hypothetical." `.okfm/level-3-enrich/index.md` renders this as the three-variant table — your
agent / **local (2+)** / credentialed — split on *who holds the key*, with only the third declaring
`needs-secrets`.

### 4. What level 3 actually asks for is unchanged by where the GPU is

DR-0013: *"A level is what OKFM asks of you before you can start, not what it costs. Level 3's ask
is something has to reason, and that is true whether the reasoning happens in a data centre or on
the laptop it was called from."* Everything level 3 exists to handle still applies: nondeterminism,
output that lands `status: draft`, the `guard` pass over the diff, and a human gate before
promotion. Meanwhile level 2's own promise — `.okfm/level-2-build/index.md`: *"Every component here
is tagged `needs-nothing`"*, backed by "extraction is not drafting" — would become false the moment
a drafting component joined it.

The same argument had already retired level 4 in DR-0009's amendment (holding the key yourself is a
change of *direction*, not a step up); DR-0013 is that argument "run in the other direction and
reaching the same place."

### 5. So the cost got a name instead of a location — and the `+` is load-bearing

The 2026-08-02 amendment records that the steward named it **Level 2+** over the record's original
argument, and it is recorded rather than quietly applied. The formulation both documents settle on:
**"The ladder measures what OKFM asks of you before you can start; the name measures what it costs
you."** Those were the same number only for as long as a model implied an API key. The amendment's
table spells out what the name does *not* change: `enrich_local.py` still declares `needs: [model]`,
still lives in the `level-3-enrich` bundle, `dev/check_levels.py` is untouched with `ALLOWED[2]`
still admitting only `human`. And it refuses to collapse the `+`: *"it is not level 2, and
pretending otherwise would make level 2's 'never needs a model' false."*

DR-0013 even prices the move you are asking about: `ALLOWED[2]` in `dev/check_levels.py` gains
`model`, the level 2 bundle takes the concept, and the promise that nothing at level 2 requires a
model stops being true — *"That is the trade, and it is not being made — the check is the only thing
keeping the promise honest as the implementation grows, and a name is not worth spending it."*

### 6. A second, independent mechanism would also break: CI on fork pull requests

Even setting the tag check aside, DR-0008's **union rule** — a composite's `needs` is the union of
its own requirements and those of everything it invokes — plus its CI gate (pull requests, including
forks, admit `needs ⊆ {}`) means one model step contaminates the whole workflow. That is why
`enrich-local` is deliberately in `EXTRA` and **absent from `STEPS`** in `dropin/okfm.py`, whose
comment says listing it "would take the whole pipeline out of CI on a fork's pull request. It stays
reachable and stays out of the run." DR-0013 records the resulting narrowing of the folder's promise
from *every component here is `needs: []`* to *every component the pipeline runs is `needs: []`*
(echoed in `dropin/README.md`). So "at level 2" in the pipeline sense is not merely disallowed by a
tag — it would cost the level 2 build its ability to run unattended on an untrusted PR.

### 7. Where the no-key fact *is* recorded, since it is genuinely true

Not as a level, but in the two places it does work:

- the absence of `needs-secrets` on the component, which is what CI and `check_levels.py` read;
- `enrich.base_url` in `dropin/config_schema.py`, which emits a `warn` finding when the host is not
  in `LOOPBACK`. DR-0013 calls this "the only place the local/credentialed boundary is written down
  in machine-readable form", justified by *"a distinction nothing checks decays into a distinction
  nothing means."* Pointing `base_url` at a public host is listed as a re-entry trigger — that is the
  `network` rung DR-0008 rejected, arriving.

One related guard worth naming, because it is what keeps the tag-based boundary trustworthy at all:
`enrich_local.py` **may not write a `needs-*` tag**. It carries existing ones over verbatim and drops
any the model proposes, because those tags are what `dev/check_levels.py` reads as fact — a model
able to write one could forge the check that keeps components inside their level (the same reasoning
DR-0008 gives for never inferring `okfm_relations`).

### In one line

Level membership is decided by `needs ⊆ ALLOWED[level]` over the exposure ladder, and
`enrich_local.py` declares `needs: [model]` because it delegates to a nondeterministic model —
which is true regardless of who owns the hardware or pays the bill. Zero cost removes `secrets`,
which it never declared, not `model`, which is the entire 2/3 line. The project's answer to your
observation is the name "Level 2+", not a move: level 2's terms plus something you supply.
