## Answer

### The misunderstanding, in one line

`build.exclude` controls **what gets read**. It does not control what the mesh **is**, and it
does not delete anything. `docs/okfm-guide/level-2-build/config-validation.md` names this exact
trap under the heading "The two keys that look like the same key": *"`exclude` says what gets
**read**. `bundles` says what the mesh **is**. Nothing connects them, and the failure that
follows is the most confusing kind available: you exclude a folder, re-run, and nothing changes
— so the tool looks broken rather than misconfigured."*

### What `build.exclude` actually does

1. `normalize()` in `dropin/okfm_core.py` lifts `build.{root,root_files,exclude,include}` into a
   flat `discover` dict.
2. `discover.exclude` is read in exactly one place: `discover_sources()` in
   `dropin/okfm_core.py`, whose inner `skipped()` helper matches each candidate directory
   against the excluded entries (in both root-relative and project-relative form, since "people
   write both").
3. `discover_sources()` is only reached through `resolve_sources()`, and only when no explicit
   `build.sources` list exists.
4. `main()` in `dropin/build.py` iterates `resolve_sources(cfg)` and calls `mirror()` per folder.

So the effect of the key is: the build stops **visiting that source folder** and stops **writing
new concepts** from it. That is the whole effect. `docs/decisions/0012-reach-is-configured.md`
and spec §13.5 (`spec/okfm-v0.2.1.md`) frame it as *reach*: "`build.exclude` drops a folder
inside a root"; recognition and readers are explicitly out of scope.

### Why the concepts are still on screen — three independent reasons

**1. The build never deletes bundle output.** The only deletion in `dropin/build.py` is
`prune_members()`, and its docstring says so: *"This is the only place the build deletes
anything, and it is deliberately narrow: `.md` files, in the mesh's own `members/` folder, that
this process wrote."* Nothing removes `.okfm/<bundle>/*.md` or its generated `index.md`. The
concepts a previous run mirrored sit there untouched. (And if `bundles` still names the excluded
id, `prune_members` won't even drop the mesh's `OKF Member` concept — its `known` set is
`set(configured_bundles(cfg)) | built | {mesh}`.)

**2. Every reader resolves bundles through `configured_bundles()`, which never looks at
`exclude`.** In `dropin/okfm_core.py`:

- if the config has a `bundles` map, that map **is** the answer, full stop;
- only when `bundles` is absent does it fall back to "every subdirectory of `build.out` holding
  at least one concept".

Either branch keeps showing the excluded folder — the first because the map still names it, the
second because the stale output directory is still on disk. `bake_web_ui.collect()` calls
`configured_bundles(cfg)` and walks `src.rglob("*.md")` under each one; so do
`dropin/check_bundles.py`, `dropin/refresh.py` and `dropin/enrich.py`. The repo's own
`okfm.json` has such a map (`mesh`, `level-1-view`, `level-2-build`, `level-3-enrich`, `docs`,
`guide`), so here the map is authoritative. Spec §13.4 states the same rule: `bundles` is an
"explicit id → path map. Its **presence turns discovery off**."

**3. Re-running the build alone never updates the viewer.** The web UI's data is a baked
`const BOOTSTRAP = {...}` block inside `okfm-web-ui.html` (see `_BLOCKS` in
`dropin/bake_web_ui.py`), rewritten only by that script — step `view` in the `STEPS` table of
`dropin/okfm.py`. `python dropin/build.py --apply` (or `okfm.py build`) does not run it, so the
page keeps rendering the previous bake regardless of anything else. The Config tab is baked too
(`current_config()`), so it also keeps showing the pre-edit `okfm.json`.

### What you actually have to change

The hint in `orphaned_bundles()` (`dropin/check_config.py`) spells out the fix, and its
docstring is a verbatim description of your symptom: *"Turning off `root_files`, or adding to
`exclude`, stops the build WRITING a bundle. It does not delete what a previous run already
wrote, and it does not touch `bundles` — so the folder sits there, stays listed, and keeps
showing up in the web UI looking like the setting did nothing."*

1. **Remove the `bundles.<id>` line from `okfm.json`** (if you have a `bundles` map). This is
   what takes it out of the mesh; `exclude` cannot.
2. **Delete the leftover output directory** — `.okfm/<id>`, i.e. `<build.out>/<id>`. Nothing in
   the pipeline will do it for you, and while the concept files are there `configured_bundles()`
   will re-adopt the folder the moment `bundles` is gone.
3. **Re-run the full pipeline, not just the build**: `python dropin/okfm.py` (config → build →
   refresh → view → check). At minimum `python dropin/okfm.py view` to re-bake
   `okfm-web-ui.html`.
4. Keep `build.exclude` as well — otherwise the next run mirrors the folder back into existence.

### Two checks that would have told you, and one lever that is not the answer

- `python dropin/okfm.py config` runs `dropin/check_config.py` first in the pipeline.
  `orphaned_bundles()` emits `warn bundles.<id> — "this build no longer writes it, but it is
  still listed and still on disk — so every reader still shows it"`, with the hint to remove the
  `bundles.<id>` line and delete the directory. Note its two guards: it returns nothing unless
  the config has a `bundles` map (`if "bundles" not in cfg or not bundles: return []`), and it
  only fires for folders carrying the build's own `generated: { by: "process:okfm-build" }`
  stamp (`_is_build_output`, matching `MINE` imported from `build.py`) — so a hand-authored
  bundle such as `guide` is never called leftover output.
- A second, different check lives in `_cross_checks()` in `dropin/config_schema.py`: it warns
  when a `bundles` entry's path equals `build.root` + the excluded entry — i.e. the **in-place**
  shape, where `bundles` points at the source folder itself. Its message is *"excluded from the
  build, but `bundles.<id>` still names it — every reader still shows it"*. For a mirrored
  bundle (whose `bundles` value points at `.okfm/<id>`, not at `docs/<id>`) that comparison
  never matches, which is why the `check_config.py` check exists as well.
- `read.exclude_scopes` is **not** the lever. It filters by a concept's `okfm_scope` frontmatter
  value, not by folder, and per its help text in `config_schema.py` it only keeps a scope "out of
  health statistics and out of any context assembled for an agent".
  `docs/okfm-guide/level-1-view/the-shipped-mesh.md` is explicit that scoped-out concepts still
  appear: the guide "renders in the web UI and counts toward nothing".
  `bake_web_ui.collect()` merely copies `"scope": scalar(block, "okfm_scope")` onto each concept
  and filters nothing out.

### One special case worth checking first

If the folder you excluded is an **in-place** bundle — files that already carry `type:`
frontmatter, like `docs/decisions/` in this repo's `okfm.json` (`build.exclude: ["decisions"]`)
— then `exclude` was always a no-op for readers by design. `mirror()` in `dropin/build.py`
already skips any file that is a concept in its own right (`if block and scalar(block, "type"):
continue`), so the build was never going to duplicate it anyway; `config-validation.md` says
"The build never had any business mirroring an in-place bundle, so excluding it was always
correct and always a no-op for readers." In that case the only way to take it out of the web UI
is to stop registering it (`bundles`, and `federation.registry` if it is the registry) — do
**not** delete the directory, because those files are your documents, not generated output.
