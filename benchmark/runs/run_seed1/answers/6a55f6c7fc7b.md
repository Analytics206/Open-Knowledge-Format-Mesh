## Answer

It is deliberate, and the stated reason is **error-attribution**: the steps form a data-dependency chain, so a step that runs after a failed one reports a *derivative* symptom, and the derivative symptom is the one people chase.

### Where the behavior lives

`dropin/okfm.py`, in `main()`'s full-pipeline loop over `STEPS`:

```python
        rc = run(script, args)
        rec.step(name, script, args, rc, time.monotonic() - t0)
        if rc != 0:
            # Stop on the first failure. A later step reading what an earlier one failed
            # to write reports a second, misleading problem.
            failed = (name, rc)
            break
```

The comment is the rationale, and it is repeated verbatim in three other places — `dropin/README.md` ("The pipeline stops at the first failure. A later step reading what an earlier one failed to write reports a second, misleading problem."), the guide document `docs/okfm-guide/level-2-build/the-pipeline.md` under the heading `# It stops at the first failure` ("Deliberately. ... and the second problem is the one people chase"), and the `description` frontmatter of the concept `.okfm/level-2-build/the-pipeline.md` ("...stops at the first failure, so the second, misleading error never appears").

### Why "misleading" is the right word here — the steps consume each other's output

`STEPS` in `dropin/okfm.py` is `config` → `build` → `refresh` → `view` → `check`, and each one reads what the previous one wrote:

- `check_config.py` validates `okfm.json`. Its docstring: "Exit 1 on an error, 0 otherwise, so the pipeline stops before building the wrong thing." The `STEPS` table has its own comment on ordering: "`config` runs first and stops the pipeline on an error. A build that reads a config with a misspelled key does not fail — it quietly does something else, and the adopter is left comparing what they wrote against what they got."
- `build.py` writes the concept files, each `index.md`, and the mesh `members/` concepts.
- `refresh.py` hashes each concept's `sources[].resource` against its recorded `okfm_captured` hash and writes `.okfm-cache/observations.json`.
- `bake_web_ui.py` bakes the `BOOTSTRAP` / `CONFIG_SCHEMA` / `CONFIG` blocks into `okfm-web-ui.html` from the bundles plus that same observation cache; `--check` exits non-zero if the committed viewer is out of date.
- `check_bundles.py` runs conformance, profile and strip-test passes over every bundle named in `okfm.json`.

So one root cause — say `build` failing partway — cascades: `refresh` reports drift or `unknown` for concepts that were never written, `view --check` reports the committed viewer out of date, and `check` reports conformance failures. Four red messages, one actual bug, and the last three are louder and further from the cause. Stopping at the first non-zero `rc` guarantees the failure you are shown is the failure you have.

### This is a house rule, not a one-off in this file

The same "suppress the derivative error" principle is applied inside individual tools, with the reasoning spelled out:

- `docs/okfm-guide/level-2-build/config-validation.md`, section `# One problem, one message`: an early version reported that a path escaped the project *and* that it did not exist — "Both were true; the second was noise, and noise is how a checker teaches people to skim it. Structural checks now run first and suppress the existence check for anything they already rejected."
- `dropin/guard.py` (comment above `MUST_UPDATE`) rejects a rule that would produce "four misleading failures every time somebody authors a decision record, which teaches people to reach for `--allow` as a matter of routine. A guard that cries wolf on the normal case is worse than no guard."

The shared premise is that spurious-but-true errors train people to skim output, which costs more than the missing information does.

### The important scope limit: fail-fast is *across* steps, not *within* one

Individual steps deliberately do **not** stop at their first error, because findings inside a step are independent rather than causally chained:

- `dropin/config_schema.py`'s `validate()` is documented as returning "Every finding, errors first," and `check_config.py` prints all of them before returning 1.
- `check_bundles.py` "Runs three passes over each bundle" and "Exits non-zero on any failure" — it collects rather than aborts.

So you still get the complete picture of what is wrong at the level where that picture is trustworthy; the `break` only prevents running steps whose inputs are known to be bad.

### What makes the cost of stopping low

Two properties in the same codebase make restarting after a fix cheap, which is what makes fail-fast affordable rather than annoying (this connection is my synthesis of the following stated facts, not a sentence in any one file):

- `docs/decisions/0008-build-pipeline.md` states the acceptance criterion for `okfm build`: "running it twice produces an empty diff," and notes a no-change release is "a fast no-op producing an empty diff." Re-running the earlier steps that already passed costs nothing.
- `dropin/build.py`'s `_owned()` guard refuses to overwrite any concept carrying a `verified:` entry or a `generated` stamp other than `process:okfm-build`, precisely so the build is safe to re-run: "a tool that eats your edits on the second run gets deleted after the second run."

### Stopping does not discard the diagnostic record

`rec.write()` in `dropin/okfm.py` is called *before* the failure return, so the telemetry run record is still emitted with the partial step list. `telemetry.py`'s `Run.write()` computes `outcome: success` only if `all(s['exit'] == 0 for s in self.steps)`, so an aborted run is recorded as `failed`, and the stderr message prints the run-record path alongside `"{name} failed (exit {rc}) — stopping"`.

### One caveat on scope

This rationale covers the pipeline *runner*'s step sequencing. The 11-step deterministic rebuild enumerated in `docs/decisions/0008-build-pipeline.md` ("`okfm build` — the `needs: []` steps, in order") is a separate, finer-grained list, and that record does not state a stop-on-first-failure rule for those internal steps. It does state a related non-fatal exception in "Settled details": "`okfm build` warns on an unfilled `[model]` field; it never fails," because failing there "would break Level 2 on something only Level 3 can fix."
