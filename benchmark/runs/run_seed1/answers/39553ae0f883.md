## Answer

Short version: it takes **two config edits, not one** — because `build.exclude` controls what
gets *read* and `bundles` controls what the mesh *is* — and the build then leaves you the
output folder, the mesh member concept, the hand-written mesh index, and every cross-bundle
edge pointing into the bundle. Only one narrow thing gets cleaned up for you.

### Why two edits

`dropin/okfm_core.py` splits the two sides deliberately:

- `resolve_sources(cfg)` decides what the build **writes**. It returns `cfg["sources"]`
  (lifted from `build.sources` by `normalize()`) if one is set, otherwise it calls
  `discover_sources()`, which rescans `build.root` live **on every build**. So the set of
  produced bundles is recomputed each run; `bundles` is never consulted.
- `configured_bundles(cfg)` decides what every **reader** sees. Its first branch is
  `if "bundles" in cfg: return {k: (base / v).resolve() ...}` — the map wins outright. This
  is what `check_bundles.py`, `refresh.py`, `bake_web_ui.py` and `enrich.py` all iterate.

`build.py` only touches `cfg["bundles"]` in `_bundle_id()` (naming relation targets) and
`prune_members()`. It never uses it to decide what to write.

Consequences, and both are failure modes the validator has explicit rules for:

- Remove the `bundles.<id>` line only → the next `okfm.py build --apply` rediscovers the
  folder under `build.root` and rewrites `.okfm/<id>/` anyway. Nothing warns, because
  `orphaned_bundles()` in `check_config.py` iterates `configured_bundles(cfg)` — once the
  line is gone the folder is invisible to the tooling entirely.
- Add the folder to `build.exclude` only → `_cross_checks()` in `config_schema.py` emits a
  warning on `build.exclude[i]`: "excluded from the build, but `bundles.<id>` still names it
  — every reader still shows it", with the hint "`exclude` controls what is READ; `bundles`
  is what the mesh IS. To drop it from the mesh, remove the `bundles.<id>` line."
- Stop producing it (via `exclude` / `root_files`) but keep the line →
  `check_config.orphaned_bundles()` warns on `bundles.<id>`: "this build no longer writes it,
  but it is still listed and still on disk — so every reader still shows it", hinting "Remove
  the `bundles.<id>` line and delete `<path>`". That check judges by the `generated.by` stamp
  (`_is_build_output()` looks for `MINE = "process:okfm-build"`), not by location, so
  hand-authored bundles under `.okfm/` are never called leftover output.

`docs/okfm-guide/level-2-build/config-validation.md` names this seam directly under "The two
keys that look like the same key", and both rows appear in its checks table.

### What to change

1. **Stop the build writing it.** In `okfm.json`:
   - a subfolder of `build.root` → add it to `build.exclude` (path relative to the root; the
     current config already does this for `decisions`);
   - the loose-files bundle (`docs` here) → set `build.root_files: false`;
   - a tree reached from outside → drop it from `build.include`;
   - if you wrote an explicit `build.sources` list, remove its entry instead — its presence
     turns discovery off (`resolve_sources`).
2. **Stop readers showing it.** Delete the `bundles.<id>` line from `okfm.json`.
3. Run `python dropin/okfm.py build --apply` **once with both edits in place**. This is the
   only run that can prune the mesh member, because `prune_members()` computes
   `known = set(configured_bundles(cfg)) | {built names} | {mesh_dir.name}` — the id must be
   absent from *both* before it is considered stale.

### What the tool cleans up, and it is one thing

`prune_members()` in `dropin/build.py` is, in its own words, "the only place the build deletes
anything, and it is deliberately narrow: `.md` files, in the mesh's own `members/` folder,
that this process wrote." Ownership is `_owned()`: no `verified:` key, and `generated` must
contain `process:okfm-build`. Anything else prints to stderr and is left alone:

```
stale  .okfm/mesh/members/<id>.md — registers `<id>`, which is not a bundle any more.
       Not mine to delete; remove it yourself.
```

**In this repository that branch always fires.** Not one member concept is build-stamped:
`members/guide.md`, `members/level-1-view.md`, `members/level-2-build.md` carry
`generated: { by: "process:okfm-scaffold", ... }`, and `members/docs.md` /
`members/level-3-enrich.md` carry `by: "agent:claude-opus-5"`. So in practice you delete the
member concept by hand. The precedent is recorded in `.okfm/mesh/index.md`, about
`docs/decisions/`: "Reinstating it is one line in `bundles`. Removing it took one, plus
deleting the member concept the build refused to throw away on its behalf."

### What is left behind for you

1. **`.okfm/<id>/` itself.** The build never deletes bundle output — `mirror()` only writes,
   and pruning is scoped to `mesh/members/`. `rm -rf .okfm/<id>/` is manual, and once the
   `bundles` line is gone nothing will ever remind you it is there.
2. **`.okfm/mesh/members/<id>.md`**, per the ownership rule above. Leave it and
   `check_bundles.py` errors: its `{ predicate: registers, target: /<id>/index.md }` no longer
   has `<id>` in `bundles`, so the target is re-rooted to `/mesh/<id>/index.md` and reported
   as "relation target /<id>/index.md resolves to nothing" — the two-steps-away symptom
   `prune_members`' docstring was written to explain.
3. **`.okfm/mesh/index.md`.** It is scaffold-stamped, so `_owned()` is false and `write_mesh()`
   skips it — the generated "Members" list never replaces it. Its "Which OKF should I read?"
   table, its "Members" table, and its links `members/<id>.md` and `../<id>/index.md` all still
   name the bundle. Deleting the folder turns those into `broken link` errors in
   `check_bundles.py`'s body-link pass.
4. **Cross-bundle edges in the bundles you keep.** `check_bundles.py` builds `mesh_paths` from
   the configured bundles and errors on any unresolvable target. Live examples here:
   `.okfm/level-2-build/index.md` → `depends_on /level-1-view/index.md`;
   `.okfm/level-3-enrich/index.md` → `depends_on /level-2-build/index.md`;
   `.okfm/level-3-enrich/the-console-app.md` → `differs_from /level-1-view/the-web-ui.md`;
   `.okfm/level-3-enrich/the-benchmark.md` → `evaluates /mesh/index.md`. Plus body links such
   as `.okfm/level-1-view/index.md` → `../level-2-build/index.md`.
5. **`.okfm/mesh/log.md`** — `type: Log`, "Append-only history of mesh membership." Nothing
   appends for you; the membership entries in it were written by hand.
6. **`dev/check_levels.py`** hardcodes `LEVELS = {"level-1-view": 1, "level-2-build": 2,
   "level-3-enrich": 3}`. Drop one of those three and it fails with
   "`<bid>`: no such bundle in okfm.json" until you edit the dict.
7. **The drift cache `dropin/.okfm-cache/observations.json`.** `refresh.py` keys entries
   `"<uri>@<bundle-id>/<relpath>"` and only ever adds — `save_cache()` rewrites the dict it
   loaded. Stale entries for the removed bundle persist; harmless (lookups are exact-key) but
   it is leftover state, and the file is explicitly rebuildable.

**Not** left behind: the committed viewer. `bake_web_ui.py` (pipeline step `view`) regenerates
the `BOOTSTRAP` / `CONFIG_SCHEMA` / `CONFIG` blocks in `okfm-web-ui.html` from
`configured_bundles`, and `--check` fails CI with "STALE: committed viewer does not match the
project". You still have to run it and commit the result. If you delete the folder while the
line is still listed it prints `warn: bundle '<id>' -> <path> does not exist`.

### Verify afterwards

`python dropin/okfm.py` runs `config → build → refresh → view → check` and stops at the first
failure. `okfm.py check` (`check_bundles.py`) is the one that catches an inconsistent removal
three ways: "`<bid>`: configured path does not exist" (line kept, folder deleted);
"`<bid>`: not registered — `<registry>` has no concept with `registers` -> /`<bid>`/index.md"
(line kept, member deleted); and the dangling-target / broken-link errors above. Also run
`python dev/check_levels.py` separately — it is not in the pipeline.

### The softer option, if you only want it to stop counting

`read.exclude_scopes` (currently `["guide"]`) plus `okfm_scope:` on the concepts keeps a
bundle out of health statistics, the injected index budget, benchmark corpora and any context
assembled for an agent, while it still renders in the web UI — described in
`.okfm/guide/deleting-this-guide.md` as "tidiness, not hygiene".

### One caveat about a shipped runbook

`.okfm/guide/deleting-this-guide.md` (and spec §14.5 around line 1247) both say `rm -rf
.okfm/guide/` is the entire procedure and that "Nothing references it. No configuration needs
editing." That holds for a vendored drop-in where the guide is not registered. It does **not**
hold in this repository as configured: `okfm.json` lists `bundles.guide`,
`.okfm/mesh/members/guide.md` carries `registers -> /guide/index.md`, and `.okfm/mesh/index.md`
links to both. Following that runbook here leaves exactly the three errors listed under
"Verify afterwards".
