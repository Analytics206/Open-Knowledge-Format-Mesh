## Answer

Because a markdown link does not contain the thing `okfm_relations` is made of. The tooling can fill `title` and `description` without a model because those are *copies*; a typed relation is not a copy of anything in the document, so producing one is drafting — and unlike a drafted description, a drafted edge is read downstream as fact. The prohibition therefore does not sit at `[model]` (which would make it a level-2 limitation a model could lift), it sits at `[human]`.

### 1. What "no model" actually buys is copying, and a link has nothing to copy

`dropin/bootstrap.py` states the rule in its own docstring — "Extraction, not drafting: every value is copied from text that already exists" — and every field it writes obeys it: `_title()` returns the first `# H1` match (`_H1`) or the de-slugged filename; `_extract_description()` returns a lead blockquote or the first chunk that survives the `_NOT_PROSE` filter. `docs/okfm-guide/level-2-build/extraction.md` gives the reason: "A drafted description is a claim. A copied one is a quotation… a description lifted verbatim from your file can be unhelpful, but it cannot be *wrong about what your file says*."

A relation entry is `{ predicate: <term>, target: <path> }`. The link supplies the target. It supplies nothing at all for the predicate, and the spec says so explicitly at §6.5 of `spec/okfm-v0.2.1.md`:

> "Links are **untyped** — the relationship kind lives in surrounding prose."

So the only part that needs inventing is the part that carries all the meaning. Choosing between `depends_on`, `part_of`, `implements`, `supports`, `contradicts`, `differs_from`, `supersedes` and the rest of `dropin/vocab/predicates.yaml` means reading the sentences *around* the link and judging which one applies. That is authoring a new claim from prose — drafting, by the project's own definition — and it is exactly the operation the level-2 build is defined by not doing. This is why `docs/decisions/0009-adoption-levels.md` splits the two into separate rows of its bootstrap table: `body links` is in the deterministic column ("markdown links preserved, **untyped**"), while `okfm_relations` is in the other one ("never inferred at all — `[human]`").

### 2. The safety argument that licenses extraction does not transfer

The worst case for an extracted description is an unhelpful sentence. The worst case for an inferred edge is a false statement that machinery then acts on. Four consumers treat `okfm_relations` as fact:

- `spec/okfm-v0.2.1.md` §7.3 — "OKFM needs typed edges for impact analysis and graph traversal."
- §8 drift model, step 4 — "Drift propagates along `okfm_relations` (bounded traversal): concepts depending on stale concepts inherit the flag." A guessed `depends_on` silently marks unrelated concepts stale.
- §17 web UI — "Typed relations (§7.3) are what make the edges mean anything — an untyped link graph shows connectivity, not meaning"; `differs_from` and `supersedes` are drawn as dashed edges. `dropin/bake_web_ui.py:relations()` is what parses them into the baked index.
- `dropin/vocab/predicates.yaml` header — "Impact analysis, drift propagation, and neighbour surfacing all read these as fact, which is why the validator REJECTS a predicate that is not listed here."

Hence the recurring formulation, in `templates/AGENTS.md` ("A wrong edge is worse than a missing one"), `dropin/README.md` ("a wrong typed edge is worse than a missing one"), and `docs/okfm-guide/level-2-build/validation.md` ("An edge asserted by a producer that guessed is worse than no edge at all"). `docs/decisions/0008-build-pipeline.md` traces the rule to a prior implementation's code comment, quoted verbatim in "Precedent: this was already solved once":

> "`relations` is CURATED, not machine-managed. Nothing here is inferred from prose — an edge asserted by a producer that guessed is worse than no edge, because traversal treats it as fact."

DR-0008's own "Against" section concedes the cost and keeps the rule: "'Never inferred' for `okfm_relations` will feel restrictive. It will."

### 3. It is a `[human]` field, so a model would not unlock it either

DR-0008's field-ownership table assigns `okfm_relations` to `[human]` with the note "Never inferred from prose. Traversal treats an edge as fact", and lists `author-relations` ("add typed edges") as a `needs: [human]` tier-2 component. That is one rung *above* `[model]`, which is the point: this is not "level 2 can't, level 3 can."

The level-3 components are held to the same line. `dropin/enrich.py` puts `okfm_relations` in `FORBIDDEN` and the brief says "Do NOT add `verified`, touch `okfm_relations`, or edit any field in: {forbidden}". `dropin/guard.py` lists it in `PROTECTED` with the reason string `"typed edges are never inferred; traversal reads them as fact"`, and `docs/okfm-guide/level-3-enrich/the-tier-guard.md` confirms it is checked even on build output, where only `okfm_captured` gets an exemption. `templates/AGENTS.md` rule 2 says the same to the adopter's agent, and adds the release valve: "Ordinary markdown links in the body are fine and encouraged." The sanctioned path for a suspected edge is a proposal, not a write — DR-0008: "A `[model]` component may *propose* relations in a review artifact; it may not write them," and its settled details put proposals in `review/`, "never to a concept."

### 4. Mechanically, the two are different kinds of pointer, and both are already handled

`dropin/check_bundles.py` processes them in separate passes and never crosses them:

- Relations pass (`--- profile: controlled predicates (spec 7.3)`): the predicate must be in `vocab/predicates.yaml` or it is an error; the target is resolved bundle- or mesh-absolute against `mesh_paths`, which is built only from files where `_FM.match` succeeds — i.e. only real concepts — and anything else errors with "relation target … resolves to nothing".
- Body-links pass (`--- body links ---`): walks the body outside fenced blocks and errors only on `broken link [{label}]({tgt})` when `(f.parent / tgt)` does not exist.

So body links are file-relative and may point at anything — a README, an image, a non-concept doc — while relation targets must be concept paths. A blind promotion of one to the other would mostly manufacture edges the validator immediately rejects. Mirror mode makes that worse: per `dropin/build.py:mirror()` and `docs/okfm-guide/level-2-build/mirror-mode.md`, the default output is a concept in `.okfm/` pointing back at an untouched source, so the prose containing the links is not even in the file the relation would be written into.

### 5. The build *does* write relations — and the exception proves the rule

`dropin/build.py` emits `okfm_relations` in exactly two places: `write_index()` adds `registered_by → /<mesh_id>/index.md`, and `write_mesh()` adds `part_of → /index.md` plus `registers → /<bundle_id>/index.md`. Nothing there is read out of prose — the build *creates* the membership from `okfm.json`'s `bundles`/`mesh` keys, so it knows the predicate the same way it knows the folder name, and `_bundle_id()` exists specifically so the target resolves against the configured bundle id rather than the folder name. `prune_members()` deletes those member concepts when the config drops a bundle, for the same reason. The federation predicates exist at all because, per §7.3 and the `federation:` comment in `predicates.yaml`, "without this edge a mesh knows its members and its *graph* does not."

The line is therefore not "the build never writes edges" but **the build may assert an edge it authored, never one it guessed**.

### 6. What is meant to happen instead

Leave the link in the body (it is preserved, resolved by the build pipeline's step 5 in DR-0008, and link-checked by `check_bundles.py`), and let a person add the predicate via the `[human]` `author-relations` step, or let an agent say so in its response or a review file. Per `dropin/README.md`, `okfm_relations` is deliberately in the "left empty" list alongside `tags`, prose sections and `verified` — an honest gap, which is the same posture as shipping `status: draft` with no `verified` entry.
