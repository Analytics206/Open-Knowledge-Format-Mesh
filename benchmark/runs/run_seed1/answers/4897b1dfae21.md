## Answer

Short version: the component that notices the change (`dropin/refresh.py`) is deliberately not a
writer of concepts, and the one field it would have to write is the field the whole signal is made
of. But the build *does* re-pin `okfm_captured` in one narrow case, so the more useful answer is
"it refuses for your concept because your concept is no longer the build's" — details below.

### 1. Knowing and re-pinning are two different components

`refresh.py` is the only thing in the system that resolves a pointer at all ("Drift is **observed
here and nowhere else**", module docstring; DR-0006). What it writes is `.okfm-cache/
observations.json`, one entry per `<uri>@<bundle/path>` key of the shape
`{"observed": "sha256:…", "observed_at": …, "resolver": "file"}` (`refresh.py` lines 138-142).
It never opens the concept for writing. It compares `observed` against the `okfm_captured.hash`
it scraped out of the frontmatter, counts `match` / `drifted` / `unknown`, prints, and exits.

That split is DR-0006's core claim: **the cache stores observations, the verdict stays derived.**
"This pointer hashed to X at time T" does not become false later, so caching it does not violate
design principle §3.4 ("record signals, not verdicts"). `okfm_captured` is the *other* stored
input to that derivation. Overwrite it and there is nothing left to derive from — the arithmetic
`observed == captured` becomes trivially true forever.

### 2. Why that specific overwrite is the forbidden one

Stated in four places, with the same reasoning each time:

- `refresh.py` closing message: drift is "a review queue, not an error… only a human refreshes
  `okfm_captured`, because doing it automatically would erase the signal it exists to carry."
- `guard.py` `PROTECTED["okfm_captured"]` = `"refreshing it automatically erases the drift signal
  it carries"`.
- `revalidate.py` docstring: refreshing a capture automatically "would erase the signal drift
  exists to carry (DR-0006)"; `docs/okfm-guide/level-3-enrich/the-human-exit.md` puts it as
  "indistinguishable from never having checked."
- `docs/okfm-guide/level-3-enrich/the-agent-contract.md`: "`okfm_captured` carries the drift
  signal. Refreshing it makes the concept agree with a source nobody reread."

The build re-stamping on your behalf would make the concept assert *I was captured from the file
as it stands* — which is a claim about a reading that did not happen. Spec §8.4 step 5 gives the
review queue three exits: re-validate, supersede, acknowledge. An automatic refresh is not a
fourth exit; it deletes the queue item without answering it.

### 3. The exit that does exist, and why it is a separate command

`python okfm/okfm.py revalidate <path> --by human:you` (`dropin/revalidate.py`). It re-pins each
source entry to the hash of the file *that entry* points at, rewrites `okfm_captured.at` to today,
and adds `verified: { by: "human:…", at: … }`. Two guards on it are the answer to your question in
miniature:

- It refuses `--by process:anything` outright (lines 79-84) — "re-validation is a human act". Per
  DR-0008's ownership table, `verified` is `[human]`: "The backfill honesty rule (§16). A set
  without `human` cannot write it." A process-actor re-validation would be that dishonesty
  "wearing a command's clothes", and worse than a script doing it quietly, because it would appear
  in the record as legitimate review.
- It imports `observe_file` from `refresh.py` rather than reimplementing the hash, "deliberately"
  — if the re-pinner and the observer differed by so much as a line ending, re-validation would
  write a value the next observation disagrees with and drift would never clear.

So the mechanics are arithmetic (that is why it is a tool at all); the *assertion* is not. Naming
a path and an actor is how you say you read the source and the concept still holds.

### 4. The signal has a second consumer that would also be destroyed

`dropin/enrich.py` derives the Level 3 work list from exactly this comparison — "Drift, and only
drift. A concept whose source hashes differently than `okfm_captured` recorded has prose that
moved since its description was extracted" (one mechanism, two uses, DR-0008 §"The `[model]`
contract" item 1). An auto-refresh would empty the enrichment queue at the same moment it emptied
the review queue. `enrich.py` also lists `okfm_captured` in `FORBIDDEN` for the model pass, and
splits the queue by `generated.by` precisely because drift is cleared by a person, not by the
drafting — otherwise "an agent following that list rewrites prose it wrote an hour ago"
(`docs/okfm-guide/level-3-enrich/the-work-list.md`).

### 5. But the build *does* re-pin — just not on your concept

This is the part that makes the rule coherent rather than absolute. `dropin/build.py`'s `mirror()`
writes a complete concept including a fresh `okfm_captured: { hash: "sha256:…", at: … }`
(line 99) on every run — but only after two filters:

- `if block and scalar(block, "type"): continue` — a source file that is already a concept in its
  own right (an in-place bundle, e.g. this repo's `docs/decisions/`, which `okfm.json` excludes
  from the build for exactly that reason) is never touched.
- `if not _owned(out_dir / f.name): continue` — `build._owned()` returns False if the destination
  has a `verified:` line, or if its `generated` field does not name `process:okfm-build`. "A
  concept stamped by a model, or carrying a `verified` entry, is somebody's work."

So on a plain build-owned draft, the rebuild *is* your refresh: the concept is regenerated from
the source and the capture moves with it. That is legitimate because there is no review signal
there to erase — nobody ever asserted anything about the old hash. `guard.py` encodes the same
boundary: `is_build_output()` duplicates `_owned()`'s logic exactly (including that `verified`
disqualifies a file regardless of stamp — "the two functions answering the same question
differently is how an exemption becomes a hole"), and grants an exemption of **one key on that
kind of file**, reporting the count as "N re-pinned by the build, not counted" rather than
dropping it silently.

The moment a person or a model touches the concept — a `verified` entry, or `generated.by` moved
off `process:okfm-build` — ownership transfers and the build stops rewriting it. That is when
`refresh` starts reporting drift at you instead, and when `revalidate` becomes the only writer.
(Note also `bootstrap.py --refresh`, the other "just recompute it" path: it recomputes
`description` only, on concepts stamped `process:okfm-bootstrap`; the hash is written on creation
and never updated there.)

### 6. Related detail: it may not even be failing your build

`refresh --check` returns 1 only for `drifted` entries whose concept `status` is `stable`
(`refresh.py` lines 167-171). "A draft is expected to be out of step with its source; that is what
draft means." A drifted stable concept is a claim that has stopped being true, which is the case
worth a person's attention.

### 7. The failure mode this rule was written from

`docs/okfm-guide/level-2-build/drift-observation.md` records that the rule was broken here, not by
decision but "by tidiness": a throwaway script re-stamped every capture after each round of edits
because a clean drift report looked like a finished job, erasing review signal for concepts nobody
had reviewed. The guard already had `okfm_captured` in its protected set and simply was not run on
scripted passes. The rule that survived is narrower than "do not refresh captures": **any edit
made by a script gets the guard run over it**, because a script sails through exactly the moments
where a person would have noticed.

### One caveat on scope

DR-0008's ownership table lists `okfm_captured` for `file://` under `needs: []` ("Hashing a local
file needs no key") and `[secrets]` for `sys://`/`store://`/`okf://`. That row is about
*capability* — which credential tier can compute the value — not a licence to re-stamp in response
to drift; the restriction on re-stamping comes from DR-0006 and is enforced by `guard.py`.
