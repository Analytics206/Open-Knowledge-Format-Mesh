## Answer

**Neither.** A pointer that has never been observed is `unknown` — a deliberate third state,
and the whole design exists to stop it collapsing into either of the other two.

### The rule

`docs/decisions/0006-drift-cost-and-caching.md` ("Three states, never two", lines 79–90):

> A pointer is `match`, `drifted`, or **`unknown`** — never observed, or observed too long ago
> to trust.
>
> Two states force a default, and the default is always the same lie: an unobserved pointer
> renders as fresh. That is the failure §3.4 exists to prevent, reintroduced through a default
> value. `unknown` renders as unknown — in the index, in the web UI, and in CI.

"§3.4" is principle 4 of `spec/okfm-v0.2.1.md` (line 93–94), *Record signals, not verdicts* —
no trust tier, staleness, drift or reconciliation status is ever frozen into a file. DR-0006's
argument is that a two-state drift field is a stored verdict smuggled back in as a default:
the concept file says nothing about drift, so a reader that must answer fresh-or-drifted has to
invent an answer, and it will always invent "fresh". `docs/decisions/index.md:117` restates it:
"a pointer that has never been observed reports `unknown` rather than defaulting to fresh."

### What "never observed" means mechanically

Observation happens in exactly one place, `dropin/refresh.py` — "Drift is **observed here and
nowhere else.** Nothing on the read path — not the web UI, not an injected index, not an agent —
resolves a pointer." A cache entry is written only when a pointer actually resolved:

```python
cache[str(uri) + "@" + rid] = {"observed": f"sha256:{observed}",
                               "observed_at": now.isoformat(timespec="seconds"),
                               "resolver": "file"}
```

Two paths bypass that write and increment `counts["unknown"]` instead:

- `uri.startswith(LIVE_SCHEMES)` — `sys://`, `store://`, `okf://`, `http://`, `https://`
  (refresh.py:40, 125–128). These need credentials, are not implemented, and "report `unknown`
  rather than guessing".
- `observe_file(target)` returned `None` because the target is not a file (refresh.py:132–136,
  logged as `unknown  <rid> → <uri> (not found)`).

A source entry missing either `resource:` or a `hash:` is skipped entirely and counted in
nothing (`if not res or not cap: continue`, refresh.py:121–122) — "no captured hash means
nothing to compare".

So "never observed" is precisely: **no key `"<uri>@<bundle/path>"` in
`dropin/.okfm-cache/observations.json`.**

### What the reader does with it

`dropin/bake_web_ui.py:drift_of()` is the reader, and it is tri-valued on purpose —
`int | None`, "1 drifted, 0 match, None never observed":

```python
pairs = _CAPTURED.findall(block)
if not pairs:
    return 0                            # nothing pinned means nothing to drift from
seen_any = False
for uri, captured in pairs:
    entry = obs.get(f"{uri}@{rid}")
    if not entry:
        continue
    seen_any = True
    if not entry.get("observed", "").removeprefix("sha256:").startswith(captured):
        return 1
return 0 if seen_any else None
```

`None` goes into the baked index's `"drift"` field (bake_web_ui.py:149) as JSON `null`, and the
docstring names the stake: "the web UI renders it `unknown`. Defaulting it to 0 would be the
stored-opinion failure spec §3.4 exists to prevent." Note this is a *comparison* of a cached
observation against the concept's `okfm_captured`, not a resolution — which is what keeps the
bake `needs: []` and keeps the viewer credential-free (DR-0006, "Who observes").

The second reader, `dropin/enrich.py:work_list()` (lines 93–96), applies the same rule from the
other side: `entry = obs.get(f"{uri}@{rid}"); if not entry: continue`. An unobserved pointer
produces **no** work item, so it is not treated as drifted either — it does not enter the
enrichment queue. With no cache at all the command refuses to report anything rather than
reporting a clean mesh: "No observations yet — run `okfm.py refresh` first" (enrich.py:81–82,
123–124; same in `enrich_local.py:276`).

In CI, `refresh.py --check` fails only on `drifted` entries whose concept `status` is `stable`
(refresh.py:169–171). `unknown` is printed, never fatal. So the answer is genuinely three-way:
fresh passes, drifted queues/fails, unknown is reported as unknown.

DR-0006 also settles the obvious edge case: "A mesh that has never been built reports every
pointer `unknown`. That is correct, and it is the honest first-run state."

### The failure mode the question is pointing at is a real, recorded bug

`docs/okfm-guide/level-2-build/drift-observation.md:17–19`:

> Defaulting `unknown` to fresh is the specific failure this design exists to prevent, and it
> is easy to reintroduce by accident: the web UI once tested `if (concept.drift)`, which turned
> every `null` into a clean bill of health. A truthy check is how two states come back.

Because the encoding is `1` = drifted, `0` = match, `null` = unknown, a JS truthy test folds
`unknown` *into* `match` — i.e. it does exactly the thing the answer to this question must not
do. Caveat: `okfm-web-ui.html` is **not present** in this directory (`okfm.json` points
`read.web_ui.path` at `./okfm-web-ui.html`), so I can confirm the tri-state value the baker
emits but cannot verify the page's current rendering code.

Nothing can smuggle a stored "fresh" in from the file side either: `dropin/check_bundles.py:23,
119–121` errors on any `okfm_(stale|drifted|drift|trust|tier|fresh):` key in frontmatter
("stores a derived verdict … spec 3.4 forbids"), and `dropin/guard.py:61` protects
`okfm_captured` because "refreshing it automatically erases the drift signal it carries".

### Two gaps I found while checking this

1. **Concept-level aggregation can mask a per-pointer unknown.** `drift_of` returns `None` only
   when *no* pinned source has an observation. A concept with two pinned sources — one observed
   and matching, one never observed — bakes as `0` (match), because `seen_any` is already True
   and the unobserved one is `continue`d past. `refresh.py` still counts that second pointer as
   `unknown`, so the pointer-level ledger and the concept-level badge disagree. Also
   `if not pairs: return 0` means a concept whose sources carry no `okfm_captured` hash reads
   `match`, not `unknown` — the unknown state requires a pinned `sha256:` with no observation.

2. **The `max_age` half of `unknown` is documented but not implemented.** refresh.py's docstring
   and DR-0006:117 both say an observation older than `max_age` reports `unknown` rather than its
   last known state. In code, `max_age`/`default_age` (refresh.py:99–100) are parsed and then only
   *printed* (line 158); every run re-observes everything and overwrites the cache, and no reader
   (`drift_of`, `work_list`) ever looks at `observed_at`. So an arbitrarily stale observation
   still reads `match`/`drifted`. Relatedly, the `drift` block DR-0006 specifies (`drift.cache`,
   `drift.max_age`) has no entry in `dropin/config_schema.py`'s `FIELDS`/`BY_PATH` and is absent
   from `okfm.json`, so an adopter who wrote it would get an `unknown_keys` error — "not a key
   anything reads" — even though `refresh.py:98` does read `cfg.get("drift", {})`.

Two smaller divergences, noted because they bear on what "never observed" is scoped to:

- DR-0006 says the cache is "Keyed by **resolved pointer URI, not by concept** … observed once
  per build rather than once per citation." The implementation keys `uri + "@" + rid` and hashes
  once per citation. Writer and both readers agree on the composite key, so it works — but it
  means unknown is per (pointer, citing concept): the same URI observed under concept A is still
  `unknown` for concept B.
- The spec text has only partly caught up with DR-0006. §3.4 (line 94) carries the amended
  build-time/cached language, but §8.4 step 2 is still two-state ("Current hash/version differs
  from `okfm_captured` ⇒ pointer marked drifted"), §14.4's badge list names only "Drifted" with no
  `unknown`, and §3.4's pointer to "§8.3" for the cache lands on §8.3 *Two orthogonal staleness
  mechanisms*, which does not name the cache. DR-0006's "Cost" section lists exactly these edits
  (§3.4, §8.3, §8.4, §8.5, §13.4, §14.4) as owed; some are outstanding.
