## Answer

**Python 3.13, and nothing else has to be installed.** That is the whole answer for the
deterministic build (Level 2, the `dropin/` folder): the runtime is the requirement, and there
is no install step of any kind before it — no `pip install`, no `requirements.txt`, no package
install, no virtualenv, no model, no key, no network.

### Where the runtime is stated

`docs/decisions/0001-runtime-and-packaging.md` is the record that decides it, and it decides two
separate things:

- **"Python 3.13, at every level."** Explicitly *not* a floor that higher levels may raise —
  the same version throughout, because "a project that runs on 3.13 at one level and 3.11 at
  another has two runtimes to explain and two sets of instructions to keep true." CI runs 3.13,
  so the supported version is the tested one.
- **"`dropin/` (Level 2) is standard library only."** No `requirements.txt`, "no install step
  beyond having Python."

The same pair is repeated everywhere the level ladder appears: `README.md` line 67 (the level
table, "2 — build … Python 3.13") and line 161 ("Python 3.13, standard library only. No install
step"); `dropin/README.md` line 97; `docs/okfm-guide/README.md` line 13;
`docs/decisions/0009-adoption-levels.md` lines 86–87 (**"Adopter supplies:** Python 3.13" /
**"Installs:** nothing"); the module docstrings of `dropin/okfm_core.py` (line 7) and
`dropin/build.py` (line 23); and the repository-layout tree in `spec/okfm-v0.2.1.md` §13.3
line 942 ("Python 3.13, standard library only. No requirements file, by design.").

### The two commands, and why there is no step before them

```bash
cp -r dropin my-project/.okfm && cd my-project
python .okfm/okfm.py             # build → refresh → view → check
python .okfm/okfm.py --check     # same four, writes nothing, fails on mismatch (CI)
```

Installation is replaced by a copy, and that is a deliberate constraint rather than a
convenience. `dropin/okfm_core.py` opens with it: "Nothing here knows where it was installed.
The folder is pasted into a stranger's project and must work from wherever it lands, so every
path is derived from this file's own location — never from a repository root, a working
directory, or an environment variable." Concretely, `HERE = Path(__file__).resolve().parent`
and `PROJECT = HERE.parent` (lines 31–32). `spec/okfm-v0.2.1.md` line 961 backs this with a
one-way import rule — `tools/` may import from `dropin/`, `dropin/` may never import from
`tools/` — "what makes Level 2 liftable by construction rather than by discipline."

### Verified against the imports, not just the prose

Every import across all 14 `dropin/*.py` files is standard library — `json`, `re`, `sys`, `os`,
`time`, `uuid`, `hashlib`, `argparse`, `difflib`, `subprocess`, `pathlib`, `datetime`,
`urllib.request`/`error`/`parse` — plus sibling modules in the same folder (`okfm_core`,
`config_schema`, `build`, `bootstrap`, `enrich`, `refresh`, `telemetry`). No third-party name
appears anywhere.

The load-bearing case is YAML. There is no PyYAML: frontmatter is parsed by hand with regex
(`okfm_core.py` `FM`, `scalar`, `frontmatter`). DR-0001 gives the evidence rather than asserting
it — "about 40 lines of regex and no PyYAML" parsing 26 concepts across 3 bundles, since the
subset of YAML the format actually uses is "scalars, lists, one level of nesting, and flow
mappings." `docs/okfm-guide/level-2-build/validation.md` ("No dependencies, on purpose") states
the cost being avoided: "A validator that needs `pip install` makes level 2 a level 2 with an
install step, and the first thing a stranger hits is a dependency resolution problem in a
language they may not use." If frontmatter ever outgrows this, DR-0001 says the answer "would be
a vendored parser, not a dependency."

### What the build also does *not* need: a model, a key, or a network

This is enforced, not just claimed. `docs/decisions/0008-build-pipeline.md` defines a closed
`needs` vocabulary — `[] < human < model < secrets` — and the rule that "a composite's `needs` is
the union of its own requirements and those of everything it invokes." `dev/check_levels.py`
turns that into a CI gate: `LADDER = ["nothing", "human", "model", "secrets"]`,
`ALLOWED = {1: set(), 2: {"human"}, 3: {"human", "model", "secrets"}}`, and every concept must
carry a `needs-*` tag (an absent one is a hard failure — "the level boundary is made of this, so
an absent one is an unchecked claim").

`dropin/okfm.py` encodes the consequence in its structure. The pipeline is the `STEPS` list —
`check_config.py`, `build.py`, `refresh.py`, `bake_web_ui.py`, `check_bundles.py` — all
`needs: []`. `enrich_local.py`, the one component that declares `needs: [model]`, sits in a
separate `EXTRA` dict, reachable by name and never in the run: "listing it in STEPS would take
the whole pipeline out of CI on a fork's pull request." So the model requirement is a Level 2+
option (`ollama pull qwen3.5:9b`, then `"enrich": {"enabled": true, "base_url": …, "model": …}`
in `okfm.json`), and both READMEs are explicit that "the model must already be pulled on that
instance — nothing here downloads one." None of that touches the deterministic build.

For contrast on the ladder: Level 1 needs only a browser and installs nothing;
Level 3 needs "an agent you already use" and OKFM still holds no credential.

### Four things worth knowing that the documentation does not say

1. **The 3.13 pin is not enforced by any code.** No file contains a `sys.version_info` check,
   there is no `pyproject.toml`/`setup.py`/`python_requires` in these files, and `okfm.py`'s
   shebang is a plain `#!/usr/bin/env python3`. The pin lives in prose and in CI; an adopter on
   an older interpreter gets a syntax or type error, not a clear message.
2. **DR-0001's "nothing in `dropin/` currently uses anything newer than Python 3.9" is wrong.**
   PEP 604 unions appear in runtime-evaluated function signatures — e.g. `okfm_core.py:111`
   `def find_config() -> tuple[Path | None, dict]:`, plus `bake_web_ui.py:54,95`,
   `bootstrap.py:132`, `build.py:117`, `config_schema.py:227,266,465`, `refresh.py:70`,
   `telemetry.py:67,80` — and no file in the repository contains
   `from __future__ import annotations` (grepped; zero matches). Those annotations are evaluated
   at definition time, so the real floor is 3.10, not 3.9. This does not change the answer
   (3.13 is what you install), but it means the DR's supporting sentence for "the pin is not
   technical" no longer holds.
3. **Whichever interpreter launches `okfm.py` is the one every step uses.** `okfm.py:65` is
   `subprocess.run([sys.executable, str(HERE / script), *args])` — there is no venv activation
   and no interpreter discovery, so `python3.13 .okfm/okfm.py` and `python .okfm/okfm.py` on a
   different default are both self-consistent.
4. **The `view` step expects `okfm-web-ui.html` to already sit beside the pasted folder.**
   `bake_web_ui.py:28` sets `VIEWER = PROJECT / "okfm-web-ui.html"` and line 186 does
   `html = VIEWER.read_text(...)` with no guard, so a missing file raises rather than skipping.
   No `.html` file exists anywhere in the files provided, and `dropin/README.md`'s file table
   does not list one as shipping inside the drop-in folder. That is a file that has to be
   *present* (as opposed to installed) for the third pipeline step, and how it gets there for a
   fresh adopter is not answerable from these files.

One adjacent requirement, outside the deterministic build: `guard.py:123` shells out to an
external `git` binary (`["git", "diff", "--unified=0"]`). That is the Level 3 `okfm.py guard`
command, not one of the four pipeline steps, so it does not add a prerequisite to the build
itself.
