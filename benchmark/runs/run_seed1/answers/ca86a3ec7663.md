## Answer

Because `okfm_captured` *is* the drift signal. It is not a cache of what the source looks
like — it is the stored half of a two-term comparison, and the build overwriting it would
resolve the comparison rather than answer it.

### The comparison, concretely

Drift is `observed_hash` vs. the stored `okfm_captured.hash`. In `dropin/refresh.py` that is
one line:

```python
if observed.startswith(captured):
    counts["match"] += 1
else:
    counts["drifted"] += 1
```

(`startswith` rather than `==` because early builds abbreviated the digest; a truncated stored
hash is compared as a prefix, so both forms work without a migration.)

If a process re-pins `captured` to `observed`, the next run matches by construction. Nothing
is fixed and nothing is recorded — the concept now agrees with a source nobody reread.
`dropin/guard.py` states the reason as the protected-field justification:
`"okfm_captured": "refreshing it automatically erases the drift signal it carries"`.
`docs/okfm-guide/level-3-enrich/the-human-exit.md` puts it as: an auto-refresh is
"indistinguishable from never having checked," and a process that resolves the signal "has
deleted the signal rather than answered it."

### The build does record what it knows — in the cache, not in your file

This is the part the question is really about. The build genuinely knows, and it writes that
down. `refresh.py` writes `.okfm-cache/observations.json`, keyed `"<uri>@<bundle>/<relpath>"`:

```json
{ "observed": "sha256:…", "observed_at": "…", "resolver": "file" }
```

It never opens a concept's frontmatter for writing. DR-0006
(`docs/decisions/0006-drift-cost-and-caching.md`) is explicit about why that is the line:
**the cache stores observations; the verdict stays derived.** "At 14:32 this pointer resolved
to `sha256:4b1e…`" never becomes false, so caching it is legal under §3.4's derive-don't-store
rule — the same category as `okfm_captured` itself. "This concept is stale" *is* a verdict, is
wrong the moment somebody fixes the source, and so is never written into a file (spec §8.4
step 3; `okfm_stale`/`okfm_drifted`/`okfm_trust` are hard build errors per DR-0008 step 3).

So the build isn't withholding knowledge. It has put the knowledge exactly where a derived
verdict can be recomputed from it, and refuses to collapse it into a stored one.

### What is actually missing is an assertion, not arithmetic

`dropin/revalidate.py` is the exit, and DR-0008 classes it `needs: [human]`. Mechanically it
is trivial — re-hash the target with the *same* `observe_file` the observer uses (imported
directly, with a comment explaining that if the re-pinner and observer differed by so much as
a line ending, drift would never clear), then rewrite `hash:` and `at:` per source entry. What
it cannot do is decide that the concept still holds against the changed source.

That is why it hard-rejects a process actor:

```python
if not by.startswith("human:"):
    print("error: re-validation is a human act — --by must be `human:<id>`", ...)
    return 2
```

and why it adds `verified: { by, at }` in the same act. Clearing drift is a claim of review,
so the record has to name who made it — a `process:` actor here would be the §16 backfill
dishonesty "wearing a command's clothes," in its most convincing form, because it would appear
in the log as a legitimate re-validation.

§8.4 step 5 gives the queue three exits, and only one needed a command: **re-validate**
(`revalidate`), **supersede** (`status: deprecated` + a `supersedes` relation), **acknowledge**
(push `stale_after` out). The last two are ordinary edits.

### The one case where the build *does* re-pin it

Worth knowing, because it looks like a contradiction. `build.py::mirror()` regenerates the
whole concept file including the capture:

```python
f'    okfm_captured: {{ hash: "sha256:{sha}", at: {stamp[:10]} }}',
```

but only past this gate:

```python
if not _owned(out_dir / f.name):
    continue                      # somebody has since worked on it — leave it alone
```

`_owned()` is true only when the file doesn't exist, or has **no `verified:` line** and its
`generated:` contains `process:okfm-build`. On such a file the same pass also re-extracts
`description` from the same source, so the capture and the prose are re-derived together and
nothing reviewed is destroyed — nobody had reviewed it. `guard.py::is_build_output()` mirrors
`_owned()` deliberately (reading the file on disk, not the diff, because a same-day rebuild
leaves `generated` out of the diff entirely; and `verified:` disqualifies regardless of stamp
— "the two functions answering the same question differently is how an exemption becomes a
hole"). The exemption is one key on that one kind of file, and it is counted out loud:
`"{exempt} re-pinned by the build, not counted"`.

The moment anyone drafts or reviews — a `verified:` entry, or `generated.by` naming a model or
a person — `_owned()` goes false, `mirror()` skips the file, and the capture freezes. That is
precisely the concept where drift carries meaning, and precisely the one the build won't
touch. Relatedly, `bootstrap.py --refresh` rewrites only `description` (its regex targets
`^description:`) and never touches `okfm_captured`, so a description refresh doesn't clear
drift either.

`enrich.py` reads the same ownership split to route the work: drift + a `process:` stamp ⇒
**"to draft"** (agent's work); drift + a human/model stamp ⇒ **"waiting on you — a draft
exists, drift stands"**, printing the `revalidate` command. `the-work-list.md` records why:
when drift alone decided the queue, every concept reappeared after the first enrichment pass
and the agent rewrote prose it had written an hour ago, differently every run — "a queue that
regenerates its own work looks busy and drains never."

### Why the rule is stated this emphatically

`docs/okfm-guide/level-2-build/drift-observation.md` records the actual failure: while these
bundles were being built, a throwaway script re-stamped every capture after each round of
edits "because a clean drift report looked like a finished job," erasing review signal for
concepts nobody had reviewed. Two things were kept from it — the defence already existed
(`guard` protects `okfm_captured`) and was run after drafting passes but not after scripted
ones, which is backwards; and nothing was forcing the tidying at all, since a drafted concept
is *expected* to drift and no check fails on it. Only `status: stable` concepts fail
`refresh --check`, so there is no build pressure that auto-refreshing would relieve. The rule
that survived is narrower than "never refresh captures": **any edit made by a script gets the
guard run over it.**

### One inconsistency in the docs, so you don't get tripped by it

`drift-observation.md` says flatly that "`okfm_captured` is only ever refreshed by a person,
through the human exit." `the-tier-guard.md` and `dropin/README.md` say a rebuild re-pins it
"on every concept whose source moved" / "legitimately." The code shows the second is true but
scoped: only on files still passing `build._owned()`. Read the first sentence as scoped to the
drift observer (its section heading is "It never clears drift for you," and `refresh.py`
indeed never writes frontmatter) and the two reconcile; taken absolutely, it overstates.

### So, in practice

```bash
python okfm/okfm.py refresh                              # see it in the queue
python okfm/okfm.py enrich                               # which queue it's in, and why
# read the source
python okfm/okfm.py revalidate <path> --by human:you     # re-pins capture + adds verified
python okfm/okfm.py refresh                              # watch it leave the queue
```

If it's a build-owned draft, a plain rebuild already handled it. If it isn't, the thing being
asked of you is not a hash — it's the judgement that the concept still holds.
