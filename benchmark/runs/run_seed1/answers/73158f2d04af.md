# 73158f2d04af

## Answer

**Neither.** A pointer that has never been observed is a third state, `unknown`, and the
whole design exists to stop a reader collapsing it into either of the other two. The rule is
stated identically in five places and implemented in code.

### The rule

`dropin/refresh.py` states it in its module docstring:

```
    match      the source hashes to what `okfm_captured` recorded
    drifted    it does not
    unknown    never observed, or observed longer ago than `max_age`

`unknown` renders as unknown. Defaulting it to `match` would be a stored opinion wearing a
computed one's clothes, which is the failure spec 3.4 exists to prevent.
```

`docs/decisions/0006-drift-cost-and-caching.md` ("Three states, never two") gives the
reasoning: *"Two states force a default, and the default is always the same lie: an
unobserved pointer renders as fresh."* And it names the first-run consequence explicitly —
*"A mesh that has never been built reports every pointer `unknown`. That is correct, and it
is the honest first-run state."* Same rule in `dropin/README.md` ("Drift" section),
`docs/okfm-guide/level-2-build/drift-observation.md`, `docs/okfm-guide/level-1-view/the-web-ui.md`
("Drift renders in three states — `match`, `drifted`, `unknown` — never two"), and
`docs/decisions/index.md` (the 0006 summary line).

### The reader does not resolve the pointer at all

That is the reason `unknown` has to exist. Under DR-0006, trust tier and staleness are
derived on every read (they are arithmetic over `verified` and `stale_after`, already in the
frontmatter), but drift is **observed during the build only** — nothing on the read path
re-resolves a pointer, "not the web UI, not an injected index, not an agent." Drift
observations live in `.okfm-cache/observations.json`, written solely by `dropin/refresh.py`.
A reader therefore has exactly two inputs: the concept's stored `okfm_captured.hash`, and a
cache entry that may or may not exist. When the entry does not exist, the reader has no basis
to say "fresh" — it has never looked.

### The code

`drift_of()` in `dropin/bake_web_ui.py` is the actual derivation, and its contract is
`1 drifted, 0 match, None never observed`:

```python
    pairs = _CAPTURED.findall(block)
    if not pairs:
        return 0                            # nothing pinned means nothing to drift from
    seen_any = False
    for uri, captured in pairs:
        entry = obs.get(f"{uri}@{rid}")
        if not entry:
            continue
        seen_any = True
        if not entry.get("observed", "").removeprefix("sha256:").startswith(captured):
            return 1
    return 0 if seen_any else None
```

`None` is emitted into the baked `BOOTSTRAP` index as JSON `null` on the concept's `"drift"`
key, and the web UI renders that `unknown`. The docstring says defaulting it to `0` "would
be the stored-opinion failure spec §3.4 exists to prevent."

Note the deliberate distinction on line 3: a concept with **no** `okfm_captured` hash at all
returns `0`, because no claim was ever pinned, so there is nothing to drift from. That is not
the same as an unobserved pointer — "a claim was made and nobody has checked it" is `null`.
`dropin/refresh.py` draws the same line (`if not res or not cap: continue` — "no captured
hash means nothing to compare").

`refresh.py` classifies as `unknown`, not `drifted`:
- any URI matching `LIVE_SCHEMES = ("sys://", "store://", "okf://", "http://", "https://")` —
  those need credentials, are not implemented, and "report `unknown` rather than guessing";
  they are never written into the cache;
- any file where `observe_file()` returns `None` because the path is missing — reported as
  `unknown … (not found)`.

### How this gets broken, per the repo's own record

`docs/okfm-guide/level-2-build/drift-observation.md` documents the exact regression:
*"the web UI once tested `if (concept.drift)`, which turned every `null` into a clean bill of
health. A truthy check is how two states come back."* So the failure mode is specifically
"unknown read as fresh," and it shipped once.

### What `unknown` does and does not trigger

It does not fail CI. `refresh.py --check` computes `blocking = [d for d in drifted if d[2] == "stable"]`
and exits 1 only on **drifted** sources in `status: stable` concepts; `unknown` entries are
printed (first 10, then a count) but never block. And `dropin/enrich.py`'s `work_list()`
skips unobserved pointers outright (`entry = obs.get(...)`, `if not entry: continue`), and
returns `(None, [])` when the cache file is absent so `main()` prints *"No observations yet —
run `okfm.py refresh` first"* rather than the misleading *"Nothing to enrich. Every observed
pointer matches…"*. Consistent: an unobserved pointer is neither a clean bill nor a task —
it is an admission that nothing was checked.

### Concretely in this checkout

There is no `.okfm-cache/` directory anywhere in the tree, so `load_observations()` returns
`{}` and every concept carrying an `okfm_captured` hash — e.g. `.okfm/level-2-build/drift-observation.md`,
which pins `sha256:e971b2…` for `../../docs/okfm-guide/level-2-build/drift-observation.md`
and `sha256:92b82a…` for `../../dropin/refresh.py` — would bake as `"drift": null`, i.e.
unknown. `okfm-web-ui.html` is also absent, so the read surface itself is not present in this
arm; the semantics above are what `bake_web_ui.py` would emit into it.

### Gaps found while answering

1. **The three-state rule is per-concept in the index, not per-pointer.** `drift_of` returns
   `None` only when *no* pointer of a concept was observed. A concept with two pinned sources
   where one was observed and matched and the other was never observed returns `0` — the
   unobserved pointer disappears behind a `match` badge at concept granularity. Both
   `refresh.py`'s report and the source-level docs speak per-pointer; the baked `"drift"`
   field cannot.
2. **The `max_age` half of `unknown` is documented but not implemented.** `refresh.py:main`
   builds `max_age` and `default_age` from `cfg["drift"]["max_age"]` and then uses
   `default_age` only in the printed line `cache: … (max_age file=3600s)`. Nothing expires a
   cache entry, and `drift_of` never reads `observed_at`. So "observed longer ago than
   `max_age`" — DR-0006's *"Past that age a pointer reports `unknown` rather than its last
   known state"*, which is also its claimed upper bound on drift latency — never actually
   fires. Only "never observed" produces `unknown` today.
3. **`drift` is not in the config validator.** `dropin/config_schema.py`'s `FIELDS` table has
   no `drift.*` entries, so the `"drift": {"cache": …, "max_age": {…}}` block DR-0006
   specified for §13.4 would be reported by `unknown_keys()` as an unknown key. The root
   `okfm.json` has no `drift` block, which is why the 3600s default applies.
4. **Cache key differs from the ADR.** DR-0006 says the cache is keyed *"by resolved pointer
   URI, not by concept"* so a query cited by many concepts is observed once per build. Both
   `refresh.py` and `bake_web_ui.py` key it `f"{uri}@{rid}"` — per URI *per concept* — so a
   shared pointer is observed and stored once per citation.
