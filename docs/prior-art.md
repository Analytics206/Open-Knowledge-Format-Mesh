# OKFM — Ecosystem and Prior Art

What else exists, what was adopted, and what was learned -- including the measurements that went against the premise. Non-normative.

### A distributable knowledge-mesh scaffolding for OKF bundles

**Version:** OKFM v0.2.1
**Baseline:** Open Knowledge Format (OKF) v0.2 — GoogleCloudPlatform/knowledge-catalog
**Concept:** Actionable Knowledge — evidence that changed what a project knows or does, preserved so the *why* stays queryable
**Date:** 2026-07-31
**Audience:** The builder, adopters of the scaffolding, and the AI agents working the codebase

## 21. Ecosystem and Prior Art

The baseline is two months old (announced June 2026) and moving. This section records
what exists, what was adopted, and what was learned — so future revisions know what
was already checked.

### 21.1 The published benchmark

`scaccogatto/okf-skills` ran the only public experiment on whether an OKF bundle
helps an agent: one repository in two states, twelve fresh agents, six questions,
blind claim-by-claim grading. Reported results, including the parts that went
against the premise:

| | with bundle | without |
|---|--:|--:|
| claims hit | 22/26 (85%) | 20/26 (77%) |
| tokens | 257,602 | 244,805 |

**The bundle cost ~5% more tokens, not fewer**, and opened more files. At n=1 per
cell the authors read this as *no measurable cost saving in either direction*, and
explicitly retired the "read three small files instead of three thousand lines"
pitch. The pattern of wins is the durable finding:

- **Won the "why" questions** — rationale that existed in exactly one place (an
  architecture decision record) and nowhere else in the repository.
- **Lost the "where do I change this" question** — a concept summarized a validator,
  dropped the detail the question needed, and the agent stopped there instead of
  reading the source. The bundle became a detour around the file with the answer.
- **Tied on everything mechanical** — constants, control flow, code comments. The
  bundle had nothing to add.

Their conclusion, adopted here as §3.13: **write down what the code cannot say.**

Two stated limits matter for interpretation: the benchmarked repository is small
(reading everything is cheap, so progressive disclosure cannot pay off) and its code
comments already explain *why* (so the bundle's advantage is suppressed). Both
conditions are the opposite of a large curated corpus, which is why §18 re-runs the
experiment rather than citing this one as settled.

### 21.2 Tooling worth adopting rather than rebuilding

The same project ships, under MIT license, several things Phase 1 would otherwise
have to write:

- A **deterministic conformance validator** (single-file, zero-config) implementing
  official §11 — the base pass under OKFM's own checks.
- A **`--migrate` mode** for v0.1 → v0.2 that is textual and idempotent, preserving
  comments, key order, and quoting. Notably, it refuses to invent `generated.by`,
  recording a process actor so migrated concepts stay honestly *unverified* — the
  behavior generalized into OKFM's backfill rule (§15).
- A **composite CI action** to gate a bundle on every push, usable with no agent
  involved.
- A **self-contained bundle visualizer** that renders a bundle as an interactive
  graph and **derives** trust tier and staleness at render time rather than storing
  them — independent confirmation of §3.4.
- A **soft-mode adoption template**: a prose contract telling an agent to read the
  index first, weigh `status` / `stale_after` / missing `verified` before relying on
  a concept, update the concept and log after changes, and validate before
  committing. A useful shape for the harness's own consume/maintain instructions.

Notably, the project ships **no automatic hooks by design** — always-on hooks
observing arbitrary sessions are intrusive and fail third-party review. Opt-in
instructions instead. Worth mirroring in harness defaults.

### 21.3 The contamination incident

Their first control arm was the repository minus its bundle directory — except a
committed static page contained the *rendered* bundle, every concept body embedded
in its inline JSON. A control agent found it and answered from the bundle's own
prose. The arm was rebuilt and the mistake published as a finding.

Generalized into §3.14: knowledge that exists in two places will be read from the
wrong one. This is an argument for reference-don't-copy across the whole design —
external stores referenced rather than absorbed, cross-bundle refs pinned rather than
duplicated, and any rendered view of a bundle treated as a derivation, never a second
home.

### 21.4 The injection finding

A second project (`guhcostan/claude-mega-brain`) measures the opposite side of the
same question and reaches the opposite headline: 0 tool calls, 100% accuracy without
tools, and roughly two-thirds fewer tokens than a wiki-plus-MCP setup.

The two results only look contradictory. §21.1 let the agent *find* the bundle; this
one **injects a compact typed index at session start** before the agent acts. Its own
comparison table settles which factor matters: a raw file dump also reaches 100%
accuracy, so knowledge presence buys the correctness — while the compressed typed
index buys roughly a quarter of the tokens and latency on top. Meanwhile the
no-injection arms collapse to 13-50% accuracy when tools are withheld, because an
agent that must decide to look often does not.

Adopted into §8.5. Also adopted: no mandated directory — a concept is recognised by its
`type:` and not by where it sits (§13.5) — a small config surface with an index budget
and type priority (§13.4), zero-overhead-when-absent, and surfacing a concept's
neighbors when it is read.

Adopted with a change: that project *scans* for frontmatter across a repository. OKFM
recognises a concept anywhere but only ever **reads** where it is told to — `build.root`,
minus `exclude`, plus `include`. The goal was incremental adoption with nothing to move,
and two explicit lists reach it without a first run that sweeps up an adopter's templates
and vendored docs.

Not adopted: that project targets OKF v0.1 (a bare `timestamp`, no `sources`,
`verified`, or `status`) and leaves types freeform with no validation. Fine for a
project wiki; insufficient for governed business numbers. Borrow the architecture,
not the schema.

One ecosystem disagreement is worth naming because it does **not** bind OKFM: §21.2's
project ships no hooks by design, holding that always-on hooks over arbitrary
sessions are intrusive, while this one is built entirely on them. OKFM resolves it by
runtime mode (§13.6) — injection where the adopter owns the runtime, a prose contract
where they do not.

### 21.5 Positioning

The ecosystem so far splits into **authoring toolchains** (validate, migrate,
visualize) and **injection plugins** (put a project's knowledge in front of an agent).
OKFM is a third thing: **scaffolding for a mesh that runs loops and writes back** —
it consumes both of the others' good ideas and adds the parts neither has. Nothing in the ecosystem so far covers the loop
family, federation, content-based drift, perspectives, or declared-versus-observed —
which is both an opportunity and a warning that those parts have no prior art to
borrow from and will have to be proven here.
