# DR-0007 — Two layers: a portable base, and an optional implementation

- **Status:** accepted 2026-08-01
- **Date:** 2026-08-01
- **Affects:** spec §13.2, §13.3, §13.6, §13.7, §14; rescopes [DR-0001](0001-runtime-and-packaging.md)

## The problem

The specification treats OKFM as one thing that an adopter installs and runs. §13.2's four
layers — core, domain pack, config, bundle — are all *implementation* layers, and §13.3's
repository tree puts `core/`, `packs/`, and `benchmark/` beside the specification as though
they ship together.

That framing makes the format contract hostage to the tooling. To find out what a legal
OKFM bundle is, you have to adopt a Python CLI.

It also contradicts the specification's own §13.6, which already lists three runtime modes
— and **mode 2 requires no code at all.** `templates/AGENTS.md` states the contract in
prose so any agent tool can follow it with nothing installed. The specification already
says OKFM must work with zero install. It just isn't built that way.

## Decision

Split into two layers with a hard boundary.

### Base — the format contract. One folder and a format.

```text
spec/okfm-v0.2.1.md      what makes a bundle legal
okfm.schema.json         the config contract
okfm-guide/              a real bundle that documents the format by being one
okfm-web-ui.html         opens from disk, no server, no build
templates/AGENTS.md      the prose contract — runtime mode 2
templates/bundle/        starter files
examples/                worked configurations
docs/                    rationale, roadmap, prior art, decisions
```

You download it, point an agent at it for documentation, and either build your own
implementation or reuse the reference one. Nothing here has a runtime, a package, or a
version to resolve.

The web UI belongs in base because it already earns its place there: it opens from
`file://` and falls back to a baked index with no server. `okfm view --serve`, which
*generates* that index, is tooling.

### Implementation — optional, replaceable.

```text
tools/
  cli/          validate, build, index, refresh, view, init, benchmark
  resolvers/    file:// okf:// store:// sys://
  validate/     conformance + profile + strip test
  inject/       index builder
  federate/     registry, cross-bundle refs, feedback ledger
  packs/        research, warehouse, codebase
  benchmark/
```

A reference implementation of the base, not a definition of it. Someone who writes their
own in TypeScript against `spec/` has an OKFM implementation, and the base is what they
conformed to.

## Structure: one repository, two areas

Not two repositories — yet.

**For:** the guide has to stay in lockstep with the specification it demonstrates; the
viewer's baked index is generated by the tooling, so a split means a cross-repo release
dance for every guide edit; the corpus checks in [DR-0004](0004-split-the-spec-preserve-numbers.md)
work because everything is in one tree; and there is one user.

**The boundary is enforced mechanically, not by intent** — the same move §13.3 already
makes with the domain-word grep:

1. Nothing under `spec/`, `okfm-guide/`, `templates/`, or `examples/` may reference
   `tools/`.
2. Base must pass its own checks with `tools/` deleted. CI runs that as an actual
   arm — delete the directory, validate the guide, open the web UI.
3. `okfm.schema.json` is base. The CLI validates against it; it does not define it.

### Re-entry trigger for two repositories

Split when the implementation earns a release cadence of its own — that is, when a tools
release needs to ship without a spec change, or a second implementation exists that needs
to pin a base version.

## The distribution test, split in two

§13.7's "stranger with a README reaches a running mesh in under an hour" was one test. It
is now two, and the first one is much stronger:

- **Base:** a stranger reads `spec/` and the guide and can hand-write a valid concept their
  own agent reads correctly — **with nothing installed.**
- **Implementation:** a stranger reaches a running mesh on their own project in under an
  hour, editing configuration and concepts only.

The first is the real portability claim. A format that needs a specific CLI to be
understood is not a format.

## Amendment 2026-08-02 — "installs nothing" was the wrong axis

This record kept saying *install*, and install is not what separates the layers. Two
corrections.

**What you take is a folder, not the project.** An adopter who wants the implementation
copies `dropin/` into their own repository as `.okfm/`. They do not clone this repository,
vendor it, or depend on it. That is the distribution claim worth making, and "installs
nothing" was standing in for it badly — the base is portable because it is *one folder and a
format*, not because a package manager is uninvolved.

**Customization brings installs, and that is fine.** Level 1 is download and look. Level 2 is
where you start changing things, and changing things reasonably means a package or a client
tool of your own choosing. What OKFM ships at level 2 stays standard-library-only, so the
folder runs the moment it lands — see [DR-0001](0001-runtime-and-packaging.md). What you add
on top is yours.

The distinction that survives is **what OKFM asks of you**, not what ends up installed in
your project. Those are different claims, and only the first is OKFM's to make.

## Against

**Two layers is overhead for one user.** True today. The counter is that the boundary is
almost free to maintain now and expensive to introduce later, once the CLI has quietly
become load-bearing for reading the format — which is exactly how a spec becomes an
implementation detail.

**The web UI blurs the line.** It is base, but its baked index is generated by tools. That
is fine and is the point of [DR-0008](0008-build-pipeline.md): the *artifact* is committed
and consumed by everyone; the *generator* is a maintainer's build step and a dependency for
nobody.
